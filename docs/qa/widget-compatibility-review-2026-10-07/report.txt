Framework inspection and alternatives
-------------------------------------
Inspected the actual ticker_provider.dart on both toolchains and compared it
byte-for-byte to each SDK HEAD Git object. Both public of(context) definitions
call dependOnInheritedWidgetOfExactType<_EffectiveTickerMode>() and return
widget?.enabled ?? true. Current valuesOf uses the SAME inherited dependency and
returns widget?.values ?? TickerModeData.fallback. Its values.enabled is set from
the same effective boolean. Missing-ancestor enabled defaults to true in both.

Both framework states calculate effective enabled as ancestorEnabled && local
widget.enabled. An enabled descendant cannot override a disabled ancestor.
Minimum updateShouldNotify checks enabled; current checks enabled OR forceFrames,
so BOTH current API calls subscribe to the same notifications, including a
forceFrames-only change. This SDK guard only consumes enabled. No ticker or
animation scheduling implementation was replaced.

No common nondeprecated public API preserves this lookup plus inherited wakeup:
- valuesOf/getValuesNotifier/TickerModeData are absent on inspected 3.38.1.
- getNotifier exists on minimum but is ALSO deprecated on current. It uses
  getInheritedWidgetOfExactType, not dependOnInheritedWidgetOfExactType. Reading
  .value alone loses wakeup on a ticker change; a listen/rebind/activate/dispose
  mechanism would add lifecycle work and is neither needed nor authorized here.
- TickerMode is StatefulWidget, so it cannot itself be the generic InheritedWidget
  dependency. Its actual effective inherited type is framework-private.
- findAncestorWidgetOfExactType<TickerMode>() reads only the nearest local flag,
  misses disabled ancestors and does not subscribe. Walking ancestors duplicates
  private framework aggregation without solving dependency notification.
- ModalRoute/isCurrent or foreground alone omit local/nested TickerMode semantics.
  Platform conditional imports do not select by Flutter SDK API version.

Therefore the two documented line exceptions are the minimal justified bridge.
The >=3.41.7 removal threshold names an actually inspected compatible version,
not an unsupported claim about the API's first release. The current deprecation
annotation says "after v3.35.0-0.0.pre" but that text does not prove availability
on 3.38.1; source proves absence there. No minimum is raised by these comments.
